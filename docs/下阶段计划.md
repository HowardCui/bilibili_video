# 本地综合网站下阶段计划（草案）

> 本文用于整理下一阶段方向，当前仍是可调整草案，不代表必须在一次开发中完成全部内容。

## 一、阶段目标

下一阶段优先建设一个在本机运行的综合网站。启动 Python 服务后，用户通过浏览器访问：

```text
http://localhost:8000
```

网站最终提供两个主要入口：

- 排行榜：展示各分区最新 Top 100、榜单变化和历史快照。
- 视频总结：提交 Bilibili 视频链接，查看处理进度和 AI 总结结果。

本阶段采用分批交付。优先让本地网站和排行榜页面可用，再逐步接入视频总结任务；不要求一次完成所有页面和未来分析功能。

### 当前项目完成情况

已经完成：

- Bilibili 全站、知识、科技、游戏和生活分区排行榜采集。
- 每个分区保存 Top 100，SQLite 已有采集任务、快照和榜单条目结构。
- 匿名请求优先，失败后使用 `.secrets/bilibili_cookies.txt` 的后备逻辑。
- 每日 00、06、12、18 点调度和启动补采判断。
- 快照实时比较，包括持续在榜、新进榜、跌出榜、排名变化、指标增量、每小时播放增长和换血率。
- 24 小时换血率阈值、空榜单状态和失败分区的 `LAST_VALID` 展示。
- 单个视频的元数据、中文字幕、文字稿、分段总结和合并总结流水线。

尚未完成或需要补强：

- 没有 HTTP 服务、浏览器页面和面向网站的 JSON 接口。
- 排行榜仓库查询主要服务于采集流程，缺少历史列表、指定快照详情等网站查询。
- 视频总结仍是同步命令行流程，没有任务 ID、进度查询、持久化状态和结果缓存判断。
- 总结与视频处理模块的异常类型不统一，尚不能安全地直接展示给网页用户。
- 目前自动化测试集中在排行榜比较和 Cookie 后备逻辑，调度器、仓库、视频处理及总结流程覆盖不足。
- README 仍描述早期架构，没有完整记录 Top 100、Cookie 后备、本地网站和当前启动方式。

## 二、已确认的决策

### 1. 建设本地综合网站

网站只监听本机地址，第一版不部署公网，不处理域名、HTTPS、账号注册和多用户权限。

```text
浏览器 → http://localhost:8000 → Python Web 服务 → 现有业务模块和 SQLite
```

### 2. 使用 FastAPI，由 Python 同时提供页面和接口

第一版使用 FastAPI 提供 HTTP 服务、HTML 页面和 JSON 查询接口。不采用前后端分离，不引入 Node.js 构建链，降低现有 Python 项目的集成成本。

### 3. 网站包含两个入口，但按优先级实施

实施顺序为：

1. 本地服务、首页和公共导航。
2. 排行榜查询接口和排行榜页面。
3. 榜单变化、历史快照和采集状态展示。
4. 视频总结提交、后台任务和结果页面。

前两项构成首个可用版本；后两项可以根据下一次开发进度继续完成。

### 4. 排行榜页面默认只读取数据

第一版页面不提供“立即采集”按钮。采集继续通过现有 CLI 和调度器运行，网站只读取 `ranking.db`，避免 Web 请求与长时间采集相互阻塞。

### 5. 比较结果继续实时计算

网站复用已有快照比较逻辑，不增加比较结果表。持续在榜、新进榜、跌出榜、排名变化、每小时播放增长和换血率均由已有快照实时计算。

超过 24 小时仍返回其他变化，但换血率不可用；采集失败时可展示上一份有效比较，并明确标记 `LAST_VALID`。

### 6. 视频总结必须以后台任务运行

字幕获取和模型调用耗时较长，HTTP 请求不能一直等待。提交视频链接后创建任务，页面通过任务 ID 查询状态：

```text
PENDING → PROCESSING → SUCCEEDED
                     ↘ FAILED
```

第一版可使用进程内单机后台执行器；任务持久化和断点恢复放在后续批次。

## 三、网站结果模型

排行榜接口应返回适合页面消费的结构，而不是直接暴露数据库行或内部对象：

```python
class RankingPageData:
    partition: str
    collected_at: datetime | None
    collection_status: str
    items: list[RankingItemData]
    comparison: SnapshotComparisonData | None
```

排行榜条目至少包含：

```text
rank, bvid, title, uploader, published_at,
views, likes, coins, favorites, comments, danmaku, shares
```

视频总结任务至少包含：

```python
class SummaryTaskData:
    task_id: str
    video_url: str
    status: str
    progress_stage: str | None
    error_message: str | None
    result: dict | None
```

Web 层负责序列化，Service 层负责业务判断，Repository 层只负责 SQLite 查询，HTML 页面不直接执行 SQL。

## 四、网站逻辑

### 排行榜访问链路

```text
选择分区
→ 查询最新成功快照
→ 查询上一份成功快照
→ 实时计算比较结果
→ 返回 JSON 或渲染 HTML
```

页面至少展示：

- 最新榜单 Top 100。
- 当前快照时间和数据新鲜度。
- 持续在榜、新进榜和跌出榜。
- 排名上升、排名下降。
- 每小时播放增长排行。
- 换血率或不可用原因。
- `CURRENT`、`LAST_VALID`、`NO_BASELINE`、`STALE` 和 `EMPTY_CURRENT` 状态。

### 视频总结访问链路

```text
提交 Bilibili URL
→ 校验并创建任务
→ 后台执行现有视频处理和总结流水线
→ 页面轮询任务状态
→ 展示结构化总结或明确错误
```

需要限制同一视频的重复任务。已有成功结果时优先复用；正在处理时返回已有任务，而不是再次调用模型。

## 五、特殊场景

### 数据库还没有榜单数据

排行榜页面显示“暂无采集数据”和 CLI 启动方式，不返回服务器错误。

### 最新采集部分失败

成功分区正常展示；失败分区展示失败原因。如果存在上一份有效比较，则明确标记为历史结果，不能伪装成本轮结果。

### 快照超过 24 小时

页面标记数据陈旧，继续展示榜单变化和增长数据，但不显示有效换血率。

### 当前榜单为空

展示 `EMPTY_CURRENT` 状态，不将上一份榜单全部判断为跌出榜。

### 视频没有中文字幕

总结任务进入 `FAILED`，展示“没有可用中文字幕”。未来接入 ASR 后再提供音频转写后备方案。

### 模型、网络或 Cookie 失败

任务记录可读错误信息，但页面不得显示 API Key、Cookie、堆栈和本地敏感路径。Cookie 继续遵循匿名请求优先、失败后才加载 `.secrets` 的规则。

### 服务重启

首批进程内任务可能中断，页面需要明确提示。任务持久化完成后，再支持重启恢复和断点续跑。

## 六、计划修改范围

增加本地网站所需依赖，预计包括 FastAPI、Uvicorn 和模板渲染依赖；具体版本在实施时结合现有 Python 3.12/3.13 范围确定。

### 新增 `web_app/`

建议目录职责：

```text
web_app/
├── app.py                  # FastAPI 应用创建与生命周期
├── ranking_routes.py       # 排行榜页面和 JSON 接口
├── summary_routes.py       # 视频总结页面和任务接口
├── ranking_queries.py      # 面向网站的排行榜读取与组装
├── summary_tasks.py        # 总结任务状态和后台执行
├── schemas.py              # Web 请求、响应模型
├── templates/              # HTML 模板
└── static/                 # CSS 和少量浏览器脚本
```

文件可按实际交付批次逐步创建，不要求第一次全部出现。

### `ranking_collector/repository.py`

补充网站所需的只读查询：分区列表、最新快照、历史快照列表和指定快照详情。避免在路由中拼 SQL。

### `ranking_collector/service.py`

保留现有采集和比较逻辑，必要时增加只读查询服务，使 CLI 与网站共用同一套状态和比较规则。

### `summarization/video_summary.py`

将完整总结流程作为后台任务调用入口继续复用。后续需要支持进度回调、已有结果复用和结构化错误，但不把 Web 逻辑写入总结模块。

### `video_processing/`

保持元数据、字幕和文字稿处理职责。补充可供任务系统识别的错误类型，避免网站只能显示笼统异常。

## 七、测试

下一阶段实施时至少覆盖：

1. 首页能够正常返回。
2. 数据库为空时排行榜页面可读。
3. 可以查询各启用分区的最新 Top 100。
4. 页面接口正确返回榜单比较状态。
5. 超过 24 小时时不返回有效换血率。
6. 采集失败时正确标记上一份有效比较。
7. 不存在的分区和快照返回明确的 404 或校验错误。
8. 视频链接为空或不是 Bilibili 链接时拒绝创建任务。
9. 重复提交同一视频时复用已有任务或结果。
10. 总结成功、无字幕、模型失败分别进入正确状态。
11. HTTP 响应不泄露 Cookie、API Key 或内部堆栈。
12. 现有排行榜采集和快照比较测试继续通过。

## 八、阶段验收标准

首个可用版本满足：

- 可通过 `http://localhost:8000` 打开本地首页。
- 首页具有排行榜和视频总结两个清晰入口；未完成入口可明确标记为后续功能。
- 排行榜页面能够读取现有 SQLite，而不是复制或伪造数据。
- 至少可以切换全站、知识、科技、游戏和生活分区。
- 可查看最新 Top 100 和快照时间。
- 可查看新进榜、跌出榜、排名变化、播放增长和换血率状态。
- 数据为空、陈旧或分区采集失败时，页面有明确状态。
- 网站启动不影响原有 `--once` 和 `--schedule` 运行方式。

视频总结批次完成后追加满足：

- 可以在页面提交 Bilibili URL。
- 总结在后台执行，页面不会因长任务一直阻塞。
- 可以查看任务进度、成功结果和失败原因。
- 同一视频不会被无控制地重复处理和重复调用模型。

## 九、暂不纳入本阶段

- 公网部署、域名、HTTPS 和云服务器运维。
- 用户注册、登录、权限和多租户。
- 在网页内启动或停止长期调度器。
- 网页直接编辑 Cookie、API Key 或其他密钥。
- React/Vue 等独立前端工程。
- WebSocket 实时推送；第一版使用普通查询或轮询。
- 无字幕视频的 ASR。
- 向量数据库和视频问答。
- 自动推荐和个性化推荐。
- 长期 UP 历史视频分析的完整实现。

## 十、已确认的展示与异常规则

- 网站为本机综合网站，通过 `localhost` 访问。
- 网站同时规划排行榜和视频总结两个入口。
- 下一阶段优先完成网站基础和排行榜，不要求一次完成全部功能。
- 排行榜第一版只读，采集继续由 CLI 和调度器负责。
- 榜单比较实时计算，不新增比较结果表。
- 排名上升按上升幅度排序，每小时播放增长按增长速度排序。
- 超过 24 小时只禁用换血率，其他比较继续展示。
- 当前榜单为空时显示独立状态。
- 采集失败时可展示上一份有效比较，并明确标记来源和时间。
- Cookie 不能通过网页显示或编辑；请求仍优先匿名，失败后再使用 Cookie。
- 页面错误信息不能泄露密钥、Cookie、堆栈或敏感本地路径。

## 十一、后续独立模块与未来功能

### 1. 上榜 UP 历史视频分析

- 在排行榜数据中增加稳定的 UP 数字 UID，不能只依赖 UP 名称。
- 识别曾经上过榜的 UP，并建立独立 UP 档案。
- 使用单独的 Bilibili UP 投稿客户端分页获取历史视频。
- 对需要分页的 Web API 实现 WBI 签名、游标、限流、缓存和失败续传。
- 保存历史投稿及其播放、点赞、投币、收藏、评论、弹幕和分享指标。
- 分析更新频率、平均表现、爆款比例、上榜频率和长期趋势。

该模块拥有独立的数据表和采集任务，不与排行榜快照表混合。

### 2. 排行榜长期趋势

- 视频首次上榜、最后在榜、连续在榜次数和累计在榜次数。
- 分区换血率时间序列。
- 视频指标增长曲线和排名轨迹。
- 分区热度变化、热门主题和周期性趋势。

### 3. 自动视频总结

- 自动挑选新进榜、快速上升或播放增长显著的视频。
- 建立待总结队列、配额限制和去重规则。
- 在榜单详情页关联已有 AI 总结。
- 对无字幕视频增加 ASR 后备流程。

### 4. 通知与报告

- 新进榜、跌出榜和快速上升通知。
- 每日或每周榜单摘要。
- 采集连续失败、Cookie 失效和模型额度异常提醒。
- 通知目标后续再选择邮件、企业微信或其他渠道。

### 5. 推荐、搜索和问答

- 按标题、UP、BV 号、关键词和分区搜索历史数据。
- 基于榜单表现和 AI 总结生成推荐。
- 引入向量库后支持针对视频内容的问答。
- 推荐结论必须保留来源快照、指标和总结依据。

### 6. 部署和运维

- 网站稳定后再评估 Docker 和公网部署。
- 增加健康检查、结构化日志、数据库备份和数据保留策略。
- 任务量增大后，再考虑 Redis、Celery 或独立任务进程。
- 在进入多用户阶段前补充认证、权限、限流和安全审计。
