# Ranking Collector 下阶段计划（草案）

> 本文用于整理下一阶段方向，当前仍是可调整草案，不代表已经进入实施。

## 一、阶段目标

完善榜单快照对比能力，让系统能够回答：

- 哪些视频仍然在榜？
- 哪些视频排名上升、下降或保持不变？
- 哪些视频是本次新进榜？
- 哪些视频已经跌出榜单？
- 在合理的时间间隔内，榜单换血程度有多高？

本阶段只对数据库已有快照进行实时比较，不新增比较结果表，不重复保存可以从原始快照推导的数据。

## 二、已确认的决策

### 1. 实时计算，不持久化比较结果

数据库继续只保存：

- 采集任务 `collection_runs`
- 分区快照 `ranking_snapshots`
- 榜单记录 `ranking_items`

Service 在需要时读取上一份快照和当前快照，临时计算并返回比较结果。暂不增加 `snapshot_comparisons`、`entered_items` 或 `exited_items` 等表。

这样可以避免重复数据，也允许比较规则改变后重新计算全部历史结果。当前每个分区只有 Top 10，实时计算成本可以忽略。

### 2. 换血率

计算公式：

```text
换血率 = 新进榜视频数 ÷ 当前榜单视频数
```

示例：

```text
上次榜单：A B C D E F G H I J
当前榜单：F G H I J K L M N O

持续在榜：F G H I J
新进榜：K L M N O
跌出榜：A B C D E
换血率：5 ÷ 10 = 50%
```

含义：

- `0%`：榜单成员完全没变。
- `50%`：当前榜单一半是新进入的视频。
- `100%`：前后榜单完全不重合。

如果接口只返回少于 10 条，则使用当前实际条数作为分母。

### 3. 24 小时限制

两份快照间隔不超过 24 小时时，正常计算持续在榜、新进榜、跌出榜、排名变化、指标变化和换血率。

超过 24 小时时：

- 继续返回持续在榜、新进榜和跌出榜。
- 继续计算排名变化、累计指标增量和每小时播放增量。
- 不计算换血率，`turnover_rate=None`。
- 比较状态标记为 `STALE`。

所有分区统一使用 24 小时阈值，本阶段不支持按分区分别配置。

### 4. 结果排序

比较结果需要同时提供两种排序：

- 排名上升榜：只包含 `rank_change > 0` 的视频，按排名上升幅度从高到低排序。
- 播放增长榜：按 `views_per_hour` 从高到低排序。

排序结果需要保持稳定；数值相同时，按当前榜单排名从高到低（排名数字从小到大）排列。

### 5. 采集失败时使用上一份有效比较

某个分区本轮采集失败时，不生成本轮比较结果，但需要读取该分区最近两份成功快照，重新计算并展示上一份有效比较。

返回和 CLI 输出必须明确标记：

```text
比较来源：LAST_VALID
提示：本轮采集失败，以下为上一份有效比较
```

历史比较必须携带实际的前后快照时间，不能伪装成本轮数据。如果历史成功快照不足两份，则只报告采集失败和“没有可用的历史比较”。

## 三、比较结果模型

计划增加统一结果模型：

```python
class SnapshotComparison:
    partition: str
    previous_collected_at: datetime | None
    current_collected_at: datetime
    elapsed_hours: float | None
    status: str
    source: str

    retained: list[RankingItem]
    entered: list[RankingItem]
    exited: list[RankingItem]
    metric_changes: list[MetricChange]

    ranking_risers: list[MetricChange]
    views_growth_ranking: list[MetricChange]

    turnover_rate: float | None
```

状态定义：

| 状态 | 含义 | 换血率 |
|---|---|---:|
| `NO_BASELINE` | 第一次采集，没有上一份快照 | `None` |
| `VALID` | 前后快照间隔不超过 24 小时 | 正常计算 |
| `STALE` | 前后快照间隔超过 24 小时 | `None` |
| `EMPTY_CURRENT` | 当前快照为空，不能判断正常换榜 | `None` |

第一次采集没有比较基准，因此不把当前所有视频标记为“新进榜”。

`source` 用于区分比较来源：

| 来源 | 含义 |
|---|---|
| `CURRENT` | 本轮成功快照与上一份成功快照的比较 |
| `LAST_VALID` | 本轮采集失败时展示的上一份有效比较 |

## 四、比较逻辑

以 BV 号作为视频标识：

```text
持续在榜 = 上次 BV 集合 ∩ 当前 BV 集合
新进榜   = 当前 BV 集合 - 上次 BV 集合
跌出榜   = 上次 BV 集合 - 当前 BV 集合
```

持续在榜的视频继续使用现有 `MetricChange` 计算：

- 播放、点赞、投币、收藏、评论、弹幕和分享增量。
- 每小时播放增量。
- 排名变化。

排名变化保持现有定义：

```text
排名变化 = 上次排名 - 当前排名
```

- `rank_change > 0`：排名上升。
- `rank_change < 0`：排名下降。
- `rank_change == 0`：排名不变。

## 五、特殊场景

### 第一次采集

```text
status = NO_BASELINE
turnover_rate = None
retained = []
entered = []
exited = []
metric_changes = []
```

### 前后榜单完全相同

全部视频属于 `retained`，`entered` 和 `exited` 为空，换血率为 `0%`。

### 前后榜单部分重合

分别返回持续在榜、新进榜和跌出榜；只为持续在榜的视频计算指标变化。

### 前后榜单完全不重合

`retained` 和 `metric_changes` 为空；当前全部视频属于 `entered`，上次全部视频属于 `exited`。间隔不超过 24 小时时换血率为 `100%`。

### 当前榜单为空

使用独立状态 `EMPTY_CURRENT`，不得执行除零：

```text
status = EMPTY_CURRENT
turnover_rate = None
retained = []
entered = []
exited = []
metric_changes = []
```

空榜单可能来自接口异常或数据异常，因此不能把上一份榜单全部判定为“跌出榜”。

### 非法比较

- 只允许比较同一分区快照。
- 当前快照时间必须晚于上一份快照。
- 条件不符时明确抛出校验异常。

## 六、计划修改范围

### `ranking_collector/config.py`

增加：

```python
TURNOVER_MAX_HOURS = 24
```

### `ranking_collector/models.py`

增加比较状态、比较来源和 `SnapshotComparison`，并校验时间、列表内容、换血率范围及状态组合。模型同时包含排名上升榜和每小时播放增长榜。

### `ranking_collector/service.py`

将当前仅返回共同视频变化量的 `calculate_snapshot_changes()` 升级或替换为：

```python
compare_snapshots(
    previous_snapshot,
    current_snapshot,
    turnover_max_hours=24,
) -> SnapshotComparison
```

`collect_once()` 返回值中的 `"changes"` 相应调整为 `"comparison"`，避免同时维护两套结果。

Service 同时负责：

- 生成按排名上升幅度排序的结果。
- 生成按每小时播放增量排序的结果。
- 识别空榜单并返回 `EMPTY_CURRENT`。
- 分区采集失败时，读取最近两份成功快照并生成 `LAST_VALID` 比较。

### `ranking_collector/ranking_collector_pipeline.py`

扩展 CLI 输出，展示持续在榜、新进榜、跌出榜、排名上升、排名下降以及换血率或不可用原因。

CLI 不只显示数量，还要同时显示视频标题和 BV 号。排名上升榜和播放增长榜按已确认规则排序。例如：

```text
排名上升：
1. 视频标题（BVxxxxxxxxxx） 上升 5 名

每小时播放增长：
1. 视频标题（BVxxxxxxxxxx） +33,333 播放/小时
```

使用历史比较时必须输出醒目标记：

```text
本轮采集失败，以下为上一份有效比较
```

同时修复当前入口，使 `--once`、`--schedule` 和 `--help` 真正通过 `main()` 执行。

### `ranking_collector/repository.py`

预计不修改数据库结构。需要补充或组合查询能力，以便在本轮采集失败时取得某分区最近两份成功快照。查询不会写入新的比较数据。


## 七、测试

至少覆盖：

1. 第一次采集没有历史基准。
2. 前后榜单完全相同。
3. 前后榜单部分重合。
4. 前后榜单完全不重合。
5. 排名上升、下降和不变。
6. 恰好间隔 24 小时，仍计算换血率。
7. 超过 24 小时，换血率为 `None`。
8. 超过 24 小时，其他指标变化继续计算。
9. 当前榜单为空时不发生除零。
10. 分区不一致时拒绝比较。
11. 当前时间早于或等于上次时间时拒绝比较。
12. CLI 正确展示 `NO_BASELINE`、`VALID` 和 `STALE`。
13. 排名上升榜按 `rank_change` 从高到低排序。
14. 播放增长榜按 `views_per_hour` 从高到低排序。
15. 排序值相同时按当前排名稳定排序。
16. 空榜单返回 `EMPTY_CURRENT`，不把全部旧视频判定为跌出榜。
17. 本轮分区采集失败时展示 `LAST_VALID` 比较并明确标注来源。
18. 历史快照不足两份时不伪造上一份有效比较。
19. CLI 同时显示视频标题和 BV 号。

## 八、阶段验收标准

- 准确识别持续在榜、新进榜和跌出榜视频。
- 准确识别排名上升、下降和不变。
- 不超过 24 小时时可以计算换血率。
- 超过 24 小时时换血率为 `None`，其他变化仍可查询。
- 第一次采集不会错误地把全部视频标记为新进榜。
- 不修改现有 SQLite 表结构和历史数据。
- 单元测试覆盖主要比较场景。
- CLI 能清晰输出比较摘要。
- 排名上升和每小时播放增长结果按确认规则排序。
- 当前榜单为空时返回独立状态，不产生误导性换榜结论。
- 分区采集失败时可以展示并明确标记上一份有效比较。
- 所有分区统一使用 24 小时阈值。
- CLI 的明细同时包含视频标题和 BV 号。

## 九、暂不纳入本阶段

- 将比较结果持久化到 SQLite。
- FastAPI 查询接口。
- 前端榜单页面。
- 趋势评分或推荐算法。
- 自动选择榜单视频生成 AI 摘要。
- 对指定up进行跨多个历史周期的长期趋势分析。
- 新进榜和跌出榜通知。

## 十、已确认的展示与异常规则

- 按排名上升幅度对上升视频排序。
- 按每小时播放增量对持续在榜视频排序。
- 当前榜单为空时使用独立状态 `EMPTY_CURRENT`。
- 分区采集失败时展示上一份有效比较，并明确标记为历史结果。
- 所有分区统一使用 24 小时换血率有效阈值。
- CLI 同时展示数量、视频标题和 BV 号。
