# 本地综合网站下阶段计划（草案）

> 本文用于整理 Shiny 本地综合网站完成后的下一阶段方向。当前仍是可调整草案，建议按批次独立设计、实现和验收，不要求一次完成全部内容。

## 一、当前基础

本地综合网站的首个版本已经完成，用户可启动 Python 服务后访问：

```text
http://localhost:8000
```

当前已经具备：

- 使用 Shiny for Python Core 构建的本地网站，只监听 `127.0.0.1:8000`。
- 排行榜和视频总结两个入口。
- 全站、知识、科技、游戏和生活分区 Top 100 展示。
- 榜单快照、实时比较、新进榜、跌出榜、排名变化、播放增长和换血率。
- `CURRENT`、`LAST_VALID`、`NO_BASELINE`、`STALE` 和 `EMPTY_CURRENT` 状态。
- 视频总结后台任务、SQLite 持久化、进度阶段、结果复用、失败重试和重启恢复。
- 深色橙金仪表盘、响应式布局及等待、处理、成功和失败动画。
- Cookie 匿名请求优先、失败后才读取 `.secrets` 的既有规则。
- 普通 pytest 函数测试；测试代码不使用测试类。

现有业务模块继续作为后续功能基础：

```text
ranking_collector/   排行榜采集、快照、比较和调度
video_processing/    视频元数据、字幕和文字稿
summarization/       分段总结与合并总结
web_app/             Shiny 页面、查询和持久化任务
```

## 二、下阶段目标

下一阶段增加九个独立功能模块：

1. 视频总结弹幕词云。
2. 排行榜长期趋势。
3. 上榜 UP 历史视频分析。
4. Codex 按需触发排行榜单次采集。
5. UP 分析数据可视化。
6. 后台运行日志与定时采集落地。
7. UP 历史视频单视频深度分析。
8. UI 友好设计与界面语言切换。
9. 数据保留、隔离清理与数据库备份。

建议实施顺序：

```text
弹幕词云
→ 排行榜长期趋势
→ 上榜 UP 历史视频分析
→ Codex 单次采集自动化
→ UP 分析数据可视化
→ 后台运行日志与 Windows 任务计划程序
→ Codex 定时自动化
→ UP 历史视频单视频深度分析
→ UI 友好设计与界面语言切换（整体界面设计稳定后）
→ 数据保留与备份（始终最后实施）
```

前三个数据功能仍按上述顺序实施。Codex 单次采集自动化与前三个模块的业务逻辑基本独立，可在任一批次后单独实现；但建议在排行榜长期趋势正式使用前完成，以确保不依赖常驻调度器也能持续产生快照。UP 分析数据可视化依赖第三批已经保存的 UP 档案、历史投稿和指标快照，因此作为第五批实施。单视频深度分析继续复用第三、第五批的历史投稿与页面能力，并在第六批日志能力完成后实施。UI 友好设计批次属于后置支线任务，只有整体页面结构、交互和视觉设计稳定后才考虑实施。

数据保留与备份当前编号为第九批，但它不是固定序号任务。后续新增任何业务功能批次时，该批次自动顺延到所有业务功能之后，始终作为最后一批维护工作实施。

九个模块必须分别拥有清晰的职责和测试边界。某一批次未完成时，不应阻塞其他已完成功能运行。

## 三、批次一：视频总结弹幕词云

> 完成状态：已完成。已接入 yt-dlp `danmaku` XML、限量解析、清洗分词、7 天缓存、非致命降级和 Shiny 词云展示。

### 1. 目标

在视频总结结果页面增加弹幕词云，用于直观展示观众讨论中的高频词和主要关注点。

弹幕词云是视频总结的补充结果，不替代字幕总结，也不改变现有总结任务的成功条件。

### 2. 数据链路

```text
提交 Bilibili 视频 URL
→ 获取视频标识和弹幕分段信息
→ 尽量获取全部公开弹幕
→ 数量上限、去重和缓存
→ 清洗、分词和停用词过滤
→ 统计词频
→ 保存词云数据
→ Shiny 结果页展示
```

### 3. 获取规则

- 尽量获取视频当前可访问的全部公开弹幕。
- 对超大视频设置弹幕数量上限，避免下载、解析和渲染耗时失控。
- 数量上限作为配置项，不散落在采集和页面代码中。
- 同一视频已有有效缓存时优先复用，不在每次打开结果页时重新请求。
- 缓存记录获取时间、弹幕数量、原始条目数和实际参与统计的条目数。
- 匿名请求优先；只有现有客户端规则要求时才使用 Cookie 后备。
- 弹幕获取失败不得让字幕总结任务失败。页面应显示“总结完成，弹幕词云暂不可用”。

### 4. 清洗与统计

至少处理：

- 空弹幕、纯标点和无意义空白。
- URL、BV 号及重复刷屏内容。
- 常见中文停用词和可配置的项目停用词。
- 同一条弹幕中的重复词。
- 过短词、纯数字和无意义符号。
- 大小写和全角、半角差异。

第一版保存词频结果，不要求保存每条弹幕的用户身份。页面只需要消费类似结构：

```python
{
    "video_id": "BV...",
    "collected_at": "...",
    "total_comments": 12000,
    "used_comments": 10000,
    "words": [
        {"text": "关键词", "count": 320},
    ],
}
```

### 5. 页面展示

- 在成功的视频总结结果中增加“弹幕词云”区域。
- 词语大小表示词频，颜色沿用网站橙、金、绿等设计 Token。
- 鼠标悬停或相邻列表展示准确词频。
- 无弹幕、获取失败、缓存过期和清洗后为空分别显示明确状态。
- 移动端允许词云缩放或使用紧凑布局，不产生横向页面溢出。
- `prefers-reduced-motion` 下不增加持续漂浮或闪烁动画。

### 6. 建议目录

```text
video_processing/
├── get_danmaku.py              # 弹幕获取与协议处理
└── danmaku_parser.py           # 弹幕解析、清洗和词频统计

web_app/summary/
├── danmaku_repository.py       # 缓存和词频持久化
└── ui.py                       # 词云结果区域
```

实际文件可在正式设计时调整，但获取、清洗、缓存和展示不能全部堆在 Shiny Server 函数中。

### 7. 验收标准

- 有公开弹幕的视频可在总结结果页看到词云。
- 重复打开相同视频优先使用缓存。
- 超大弹幕量受到明确上限控制。
- 无弹幕或弹幕获取失败不影响已有 AI 总结结果。
- 页面不显示 Cookie、请求签名、堆栈、本地路径或弹幕用户身份。
- 清洗、词频、缓存和异常降级均有普通 pytest 函数测试。

## 四、批次二：排行榜长期趋势

> 完成状态：已完成。已实现时间范围查询、视频在榜统计、排名与累计指标轨迹、分区换血率、缺失区间、240 点限制和 Shiny 原生 SVG 展示。

### 1. 目标

在现有“最新快照比较”的基础上增加跨多份快照的长期趋势，让用户可以观察视频、UP 主和分区随时间的变化，而不只比较最近两次采集。

### 2. 分析范围

第一版至少提供：

- 视频首次上榜时间和最后在榜时间。
- 连续在榜次数和累计在榜次数。
- 视频历史最高排名、最低排名和当前排名。
- 视频排名轨迹。
- 播放、点赞、投币、收藏、评论、弹幕和分享的增长曲线。
- 分区换血率时间序列。
- 分区上榜视频数量和有效快照数量。
- 分区热度变化。

热门主题和周期性趋势可在基础时间序列稳定后继续增加，不作为第一批强制验收条件。

### 3. 时间范围

页面提供固定时间范围：

```text
24 小时、7 天、30 天、全部
```

查询必须限制返回点数。数据量增大后，可按小时、天或周聚合，不应一次把全部原始榜单条目发送到页面。

### 4. 数据策略

- 原始排行榜快照继续作为事实来源。
- 第一版优先实时查询和按范围聚合，不急于新增重复的比较结果表。
- 对计算成本高且重复使用的长期指标，可增加可重建的派生表或缓存表。
- 派生数据必须记录来源快照范围和更新时间。
- 派生表可以从原始快照重新生成，不能成为唯一事实来源。
- 当前已有的 `LAST_VALID`、陈旧快照和空榜单规则继续适用。

### 5. 页面设计

排行榜入口增加长期趋势区域或二级页面：

- 视频排名轨迹图。
- 视频指标增长图。
- 分区换血率趋势图。
- 长期在榜视频列表。
- 首次上榜和重新上榜列表。
- 时间范围选择和分区筛选。

页面应明确显示数据范围、样本点数量、最近快照时间和是否存在缺失区间。

### 6. 查询边界

建议增加：

```text
web_app/trends/
├── __init__.py
├── queries.py                  # 时间范围和聚合查询
├── service.py                  # 长期指标计算
├── ui.py                       # 趋势页面
└── server.py                   # Shiny 响应式绑定
```

`ranking_collector.repository` 只增加通用的历史读取能力；趋势指标计算放在趋势 Service 中，Shiny UI 不直接执行 SQL。

### 7. 特殊场景

- 数据不足两个快照时显示“趋势数据不足”。
- 采集时间不连续时保留真实时间间隔，不伪造等间隔数据。
- 分区采集失败时图表显示缺口，不自动用上一份数据填平。
- 视频跨分区出现时，默认按分区分别统计；跨分区合并需要明确选择。
- 指标出现平台校正或下降时保留实际值，不强制改成零增长。

### 8. 验收标准

- 可以按分区和时间范围查看长期趋势。
- 可以查看指定视频的排名轨迹和指标曲线。
- 首次、最后、连续和累计在榜统计准确。
- 换血率趋势复用现有口径，不产生另一套含义不同的算法。
- 缺失、失败和陈旧区间显示清楚。
- 大范围查询有点数限制和聚合策略。
- Repository、Service 和页面转换逻辑使用普通 pytest 函数测试。

## 五、批次三：上榜 UP 历史视频分析

### 1. 目标

识别曾进入项目排行榜的 UP 主，建立稳定的 UP 档案，采集其历史投稿并分析更新频率、平均表现、爆款比例、上榜频率和长期趋势。

第一版只分析“曾进入项目排行榜的 UP 主”，不扩展为任意 UP 主搜索和全站爬取。

### 2. 稳定身份

- 排行榜采集从下一次实现开始保存 UP 数字 UID，例如 Bilibili `mid`。
- UP 名称只用于展示，不能作为关联主键。
- 旧快照只有 UP 名称时，不根据名称猜测 UID。
- 旧数据可在未来通过明确、可验证的来源回填 UID；无法确认时保持未知。
- UP 改名后仍通过数字 UID 关联同一档案，并保留最近显示名称。

需要扩展排行榜条目模型和表结构：

```text
uploader_id, uploader_name
```

迁移必须兼容旧 SQLite 数据，旧记录的 `uploader_id` 允许为空。

### 3. 数据链路

```text
排行榜出现带数字 UID 的 UP
→ 建立或更新 UP 档案
→ 创建历史投稿采集任务
→ 分页获取 UP 投稿
→ 保存投稿基础信息和指标
→ 支持断点续传和增量更新
→ 计算 UP 分析指标
→ Shiny 页面展示
```

### 4. Bilibili 客户端要求

- 使用独立的 UP 投稿客户端，不把分页、签名和限流逻辑写进排行榜客户端。
- 需要分页的 Web API 实现 WBI 签名。
- 支持游标或页码持久化，失败后从最近成功位置继续。
- 设置请求间隔、随机抖动、重试上限和退避。
- 匿名请求优先，需要时才使用 Cookie 后备。
- 对账号不存在、投稿不可见、访问受限和风控分别记录安全状态。
- 不在日志和页面显示 Cookie、签名原始材料或本地敏感路径。

### 5. 数据表建议

```text
uploader_profiles
    uploader_id
    current_name
    first_ranked_at
    last_ranked_at
    updated_at

uploader_collection_tasks
    task_id
    uploader_id
    status
    cursor
    started_at
    updated_at
    finished_at
    error_code

uploader_videos
    uploader_id
    bvid
    title
    published_at
    duration
    partition
    latest metrics...

uploader_video_snapshots
    uploader_id
    bvid
    collected_at
    metrics...
```

UP 历史投稿、采集任务和指标快照使用独立表，不与排行榜快照表混合。

### 6. 第一版分析指标

- 投稿总数和统计时间范围。
- 最近发布时间和平均更新间隔。
- 周、月或季度投稿频率。
- 播放、点赞、投币、收藏、评论、弹幕和分享的中位数与平均值。
- 高于该 UP 自身历史基线的视频比例。
- 爆款视频列表和爆款比例。
- 首次上榜、最近上榜、累计上榜视频数和累计上榜次数。
- 上榜视频与普通历史视频的表现对比。
- 视频发布后进入榜单的大致时间差。

爆款不能只使用固定播放量阈值。第一版建议以 UP 自身历史分位数为主，并在正式设计时确定口径。

### 7. 页面设计

UP 历史视频分析必须放在独立子界面中，与排行榜主界面的快照和变化区域分开。侧边栏增加“UP 分析”入口；排行榜中的 UP 名称可以作为进入对应 UP 详情的快捷链接，但分析内容不直接展开在排行榜主界面。

页面至少展示：

- UP 基础档案和最近更新时间。
- 投稿频率趋势。
- 历史视频表现分布。
- 爆款视频和上榜视频。
- 上榜频率及排名表现。
- 历史投稿采集状态、进度和失败原因。
- 数据范围、样本数量和指标口径说明。

第一版即提供独立“UP 分析”子界面，不将独立入口推迟到后续版本。

### 8. 增量更新

- 第一次采集获取允许范围内的历史投稿。
- 后续采集优先检查新投稿，并更新近期视频指标。
- 较老视频降低刷新频率，避免每次全量更新。
- 已完成页面保存最新成功游标和更新时间。
- 服务重启后未完成任务可以恢复或安全重试。
- 同一 UP 同一时间最多一个活跃采集任务。

### 9. 特殊场景

- 旧排行榜记录没有 UID：显示“身份未确认”，不创建采集任务。
- UP 改名：更新当前名称，历史数据仍按 UID 关联。
- 投稿被删除或转为不可见：保留历史记录并标记状态。
- WBI 或风控失败：停止过度重试，记录可读错误并等待后续重试。
- 样本过少：不输出看似精确的爆款比例和频率结论。
- 指标下降：保留平台返回值并记录采集时间，不擅自修正。

### 10. 验收标准

- 新排行榜数据保存稳定的 UP 数字 UID。
- 旧数据在 UID 未确认时不会按名称错误合并。
- 可以为曾上榜的 UP 创建并恢复历史投稿采集任务。
- 分页、WBI、限流、缓存和失败续传正常工作。
- 同一 UP 不会重复创建活跃采集任务。
- UP 档案、投稿、指标快照与排行榜快照相互独立。
- 可以查看投稿频率、表现分布、爆款和上榜情况。
- UP 历史视频分析显示在独立子界面中，不占用排行榜主界面。
- 页面明确显示样本范围、更新时间和失败状态。
- 客户端、Repository、Service 和页面转换逻辑均有普通 pytest 函数测试。

## 六、批次四：Codex 按需触发排行榜单次采集

> 完成状态：已完成。包装入口、进程级并发锁、超时终止、遗留任务处理、SQLite 结果验证、安全文本/JSON 报告和稳定退出码均已实现。定时调度的正式落地移至第六批；当前 Codex 定时自动化保持暂停。

### 1. 目标

排行榜采集不要求本机长期运行 `--schedule` 进程。由 Codex 自动化、操作系统计划任务或用户在 Codex 中发出的明确指令，在需要时启动一次采集；采集完成、失败或超时后进程退出，并向用户汇报结果。

该批次不重写排行榜采集器，而是安全复用现有单次采集入口：

```powershell
python -m ranking_collector.ranking_collector_pipeline --once
```

现有 `--schedule` 继续保留为可选后备，不要求删除，也不与 Codex 自动化同时运行。

### 2. 触发方式

支持两类触发：

- 定时触发：Codex 自动化或本机计划任务在约定时间唤醒并执行一次采集。
- 人工触发：用户在 Codex 中明确说“采集排行榜”等指令时执行一次采集。

建议定时时间继续沿用现有采集节奏：

```text
每天 00、06、12、18 点
```

具体时区必须明确记录，默认使用运行电脑的本地时区。自动化只负责唤醒和运行单次任务，不在后台维持一个长期 Python 进程。

### 3. 执行链路

```text
Codex 自动化或人工指令触发
→ 检查项目目录和 Python 环境
→ 检查是否已有排行榜采集正在执行
→ 运行现有 --once
→ 等待单次采集结束
→ 查询本次 collection_run 和各分区结果
→ 验证成功快照与条目数量
→ 向用户汇报成功、部分失败或完全失败
→ 进程退出
```

Codex 不应仅根据命令退出码判断成功。执行完成后还要读取 SQLite 中对应的采集任务和分区结果，确认数据是否真正写入。

### 4. 防重复与并发

- 同一时间最多运行一个排行榜采集任务。
- 触发前检查数据库中的未结束 `collection_run`，必要时结合进程级互斥锁。
- 如果已有有效采集正在执行，新触发应跳过并汇报“已有采集任务运行中”。
- 不因为重复触发创建两套相同时间点的快照。
- 长时间未结束的记录不能直接当作活跃任务；应根据超时阈值标记为疑似中断，并要求安全恢复或人工确认。
- Codex 自动化和保留的 `--schedule` 不应同时启用。文档必须提示用户只选择一种主要调度方式。

### 5. 环境与权限

- 自动化必须在项目根目录运行。
- 使用项目已配置的 Python 环境，不临时下载未知依赖。
- 需要网络访问时遵循 Codex 或操作系统的授权规则。
- `.env`、Cookie 和数据库路径沿用项目配置，不把密钥写入自动化提示词、日志或通知。
- 工作目录不存在、Python 环境损坏或依赖缺失时停止执行并汇报，不自动修改业务代码。
- 自动采集只允许调用既有采集命令，不授权 Codex提交 Git、修改源代码或执行其他任务。

### 6. 结果汇报

每次触发至少汇报：

- 触发来源：定时或人工。
- 开始时间、结束时间和总耗时。
- 本次 `collection_run` ID。
- 全站、知识、科技、游戏和生活各分区状态。
- 每个成功分区保存的条目数量和快照时间。
- 失败分区的安全错误摘要。
- 是否使用 `LAST_VALID`，以及对应历史时间。
- 整体状态：`SUCCEEDED`、`PARTIAL_FAILED`、`FAILED`、`SKIPPED_ALREADY_RUNNING` 或 `TIMED_OUT`。

汇报不得包含 Cookie、请求头、堆栈、API Key 或敏感本地路径。

### 7. 超时与失败策略

- 单次采集设置明确超时，不允许自动化无限等待。
- 部分分区失败时保留成功分区结果，并汇报 `PARTIAL_FAILED`。
- 网络或 Cookie 失败时遵循现有匿名优先、Cookie 后备逻辑，不由自动化层实现另一套请求策略。
- 失败后不立即无限重试。第一版最多执行一次受控重试，或等待下一个计划时间。
- 连续失败达到阈值时停止自动重试并提醒用户检查网络、Cookie 或 Bilibili 接口状态。
- 自动化被取消、电脑休眠或重启时，下一次运行先检查遗留任务状态。

### 8. 实现边界

建议提供一个轻量的、可独立验证的包装入口，例如：

```text
automation/
├── __init__.py
├── ranking_once.py            # 调用单次采集、超时和结果验证
└── reports.py                 # 安全结果摘要
```

包装入口负责：

- 环境和并发检查。
- 调用既有采集 Service 或 CLI 单次入口。
- 将数据库记录转换为结构化执行结果。
- 为 Codex 自动化返回清晰退出状态。

它不负责：

- 重新实现排行榜客户端。
- 修改排行榜算法。
- 长期驻留后台。
- 控制 Shiny 服务生命周期。
- 自动提交代码或更改项目配置。

### 9. Codex 自动化配置原则

- 自动化提示应简短、固定且操作范围明确。
- 提示中写明项目目录、只运行单次采集、需要验证 SQLite、需要汇报结果、不得修改代码。
- 自动化使用固定计划时间时，记录时区和启用状态。
- 自动化执行历史应可查看，方便判断某个时间点是否已经运行。
- 修改时间、暂停或删除自动化由用户明确操作，不由采集任务自行改变计划。
- 如果当前 Codex 环境不支持可靠的定时唤醒，可使用 Windows 任务计划程序调用同一个包装入口；业务代码和验证规则保持一致。

### 10. 测试

- 使用普通 pytest 函数测试包装入口，不写测试类。
- 使用临时 SQLite 验证成功、部分失败、完全失败和重复运行。
- 使用依赖注入替换真实网络采集，不在自动测试中请求 Bilibili。
- 验证已有任务时正确跳过。
- 验证超时、取消和中断记录的处理。
- 验证数据库确实出现对应快照和分区结果后才报告成功。
- 验证安全汇报不会泄露 Cookie、密钥、堆栈和本地路径。
- 验证包装入口结束后没有残留后台线程或长期 Python 进程。

### 11. 验收标准

- 不启动 `--schedule` 也能由 Codex 或计划任务执行一次完整采集。
- 采集结束后 Python 进程退出，不需要长期挂在后台。
- 定时和人工触发都复用同一个安全包装入口。
- 重复触发不会产生并发采集或重复快照。
- 结果以数据库写入为准，不只依赖命令退出码。
- 可以清楚看到每个分区的成功或失败状态。
- 超时、部分失败、连续失败和遗留任务都有明确处理。
- 自动化不修改源代码、不操作 Git、不显示密钥。
- 保留的 `--once`、`--schedule` 和 Shiny 网站继续正常运行。

## 七、批次五：UP 分析数据可视化

> 完成状态：已完成并通过 Web 端手动验收。已实现投稿频率、表现趋势、表现分布、上榜对比、爆款比例、指标切换和原生响应式图表；验收期间同时修复了 UP 历史指标补全及分批采集暂停、续传状态。

### 1. 目标

在现有独立“UP 分析”子界面中增加数据可视化区域，把已经计算的投稿节奏、视频表现、爆款和上榜情况转换为直观图表，帮助用户快速判断 UP 的更新规律与历史表现变化。

第五批只消费第三批已经写入 SQLite 的数据，不增加新的 Bilibili 爬取接口，不改变历史投稿采集任务的成功条件，也不修改排行榜、视频总结和弹幕词云页面。

### 2. 页面位置

可视化图表必须放在“历史投稿”板块上方，页面顺序固定为：

```text
UP 基础档案与采集操作
→ 指标摘要
→ 数据可视化图表
→ 历史投稿列表
```

图表使用与现有网站一致的深色橙金卡片、边框、间距和响应式布局，不增加风格不同的独立仪表盘。

### 3. 第一版图表

第一版至少提供：

- 投稿频率趋势：按月统计投稿数量，观察更新节奏和断更区间。
- 视频表现趋势：按发布时间展示播放量变化，并允许切换点赞、投币、收藏、评论、弹幕和分享。
- 历史表现分布：展示播放量中位数、平均值和高表现区间，避免只被单个爆款误导。
- 上榜与普通投稿对比：比较两组视频的平均或中位播放表现，并显示各自样本数。
- 爆款比例：按 UP 自身历史基线展示爆款与普通视频数量和占比。

同一张图不同时堆叠全部指标。播放、点赞等数量级差异较大的指标通过单选切换，保证图表可读性。

### 4. 数据来源与口径

图表只读取现有表：

- `uploader_profiles`：UP 身份和上榜时间范围。
- `uploader_videos`：历史投稿、发布时间和最新指标。
- `uploader_video_snapshots`：同一视频跨采集时间的指标快照。
- `ranking_items`：视频上榜次数、最好排名和首次上榜时间。

投稿频率以视频发布时间为准；表现趋势默认使用 `uploader_videos` 中的最新指标；需要观察同一视频增长时才读取 `uploader_video_snapshots`。爆款口径继续沿用第三批的 UP 自身历史分位数，不另设固定播放量阈值。

所有图表必须同时返回样本数量、统计时间范围和指标名称，不能只返回没有口径说明的图形。

### 5. 查询与渲染边界

- 图表查询放在 `web_app/uploader/queries.py` 或独立的 uploader 图表查询模块中。
- 聚合、分组和指标计算保持为普通 Python 函数，不写入 Shiny 响应式函数内部。
- 图表优先复用项目已有的原生 HTML、CSS 和 SVG 渲染方式，不新增重量级前端图表框架。
- 单次页面查询设置数据点上限；投稿过多时按月聚合或抽样，不直接渲染无限数量的 SVG 节点。
- 切换 UP 或指标时只更新图表数据，不重新发起历史投稿网络采集。

### 6. 交互要求

- 默认展示播放表现趋势。
- 用户可以切换播放、点赞、投币、收藏、评论、弹幕和分享指标。
- 图表按时间从旧到新排列。
- 上榜视频需要使用与普通投稿不同但符合现有配色体系的视觉标识。
- 图表标题附近显示当前样本数和数据更新时间。
- 移动端改为单列排列，不要求横向拖动整个页面才能查看图表。

### 7. 空状态与异常状态

- 没有选择 UP：显示选择提示，不渲染空坐标轴。
- 尚未采集历史投稿：保留采集入口，并说明需要先采集数据。
- 样本数量不足：显示实际样本，不输出爆款比例或稳定趋势结论。
- 某项指标全部为零或缺失：该图显示“暂无可用指标”，其他图继续展示。
- 历史采集失败但已有旧数据：继续展示上一份有效数据，并明确标注更新时间和失败状态。
- 查询失败：只让可视化区域降级，不影响 UP 档案和历史投稿列表。

### 8. 测试

- 使用普通 pytest 函数测试月度聚合、指标切换、上榜分组和爆款比例，不写测试类。
- 使用临时 SQLite 验证图表查询结果，不访问真实 Bilibili。
- 覆盖无数据、单条数据、全零指标、缺失快照和大量投稿聚合。
- 页面测试验证可视化区域位于历史投稿板块之前。
- 验证新增图表不会触发网络采集，也不会修改数据库。
- 原有排行榜、视频总结、词云、长期趋势和 UP 历史投稿测试继续通过。

### 9. 验收标准

- UP 分析页面在历史投稿列表上方展示独立可视化区域。
- 可以查看投稿频率、视频表现趋势、表现分布、上榜对比和爆款比例。
- 指标切换不会重新采集数据，也不会刷新无关页面板块。
- 每张图都有样本数量、统计时间范围和明确指标口径。
- 样本不足、全零指标、采集失败和查询失败均有独立安全状态。
- 桌面端与移动端布局均保持现有深色橙金视觉风格。
- 不新增爬取接口和数据表，不影响第三批已经跑通的采集与历史投稿展示。
- 所有新增逻辑通过普通 pytest 函数测试，并由用户完成页面手动验收。

## 八、批次六：后台运行日志与定时采集落地

> 小批 A 完成状态：已完成并验收。统一 JSON 文件日志、北京时间、脱敏、按大小轮转、安全降级和业务事件接入已实现；Windows 任务计划程序已按北京时间四个时点启用，并通过一次立即运行完成真实采集、日志和 SQLite 验收。小批 B 尚未开始，Codex 定时自动化继续保持暂停。

### 1. 目标

为排行榜采集、视频总结、弹幕处理、UP 历史投稿采集、单次采集和 Shiny 服务建立统一的后台日志能力，让开发者可以通过项目内日志文件判断任务何时开始、运行到哪一步、为何失败，同时避免依赖终端滚动输出排查问题。在日志能力稳定后，先落地 Windows 任务计划程序，再处理 Codex 定时自动化。

后台日志用于运行诊断，不替代 SQLite 中的业务任务、快照和结果记录，也不能把日志当作任务状态的唯一事实来源。

### 2. 实施分批

#### 2.1 小批 A：后台日志与 Windows 任务计划程序

- 先完成本批次的统一日志、脱敏、轮转、容量限制和日常检查方式。
- Windows 任务使用项目已验证的 `.venv`，在项目根目录执行 `automation.ranking_once --json`，不启动常驻 Python 调度进程。
- 计划时间使用北京时间每天 `00:00、06:00、12:00、18:00`，并提供创建、查看、立即运行、暂停和删除任务的方法。
- 任务输出、进程退出码、SQLite `collection_run` 和项目日志必须能关联同一次运行。
- 先完成一次人工启动和一次任务计划程序触发验收，再进入小批 B。

#### 2.2 小批 B：Codex 定时自动化

- 仅在小批 A 和项目日志验收通过后开始，继续只调用 `automation.ranking_once --json`。
- 明确验证 bundled Python 的项目依赖加载、Bilibili 联网权限、非零退出码下的 JSON 捕获和本轮 `run_id` 汇报。
- 不允许 Codex自行实现第二套 SQLite 查询、读取历史成功 run 冒充本轮结果，或获得通用 Python 持久执行权限。
- 完成一次真实手动验收后，Windows 与 Codex 只能选择一个作为启用中的定时方案；另一方案必须暂停，并在 README 中记录切换方法。
- 若无法在最小权限下稳定联网，Codex 自动化继续保持暂停，Windows 任务计划程序作为正式方案，不因此阻塞本批次其他日志能力。

### 3. 覆盖范围

第一版至少覆盖：

- Shiny 服务启动、停止和未处理异常。
- 排行榜单次采集的开始、分区结果、结束、超时和跳过。
- 视频总结任务的排队、元数据、字幕、分段总结、合并、词云和失败阶段。
- UP 历史投稿采集的开始、分页进度、风控、后备请求、恢复和结束。
- Codex 或计划任务触发来源、执行状态和 `collection_run` ID。

每条日志至少包含时间、级别、模块、事件名称、可选任务 ID 和安全消息。禁止只输出无法检索的自由文本堆栈。

### 4. 日志结构

统一使用 Python `logging`，并提供稳定的结构化字段：

```text
timestamp
level
module
event
message
task_type
task_id
run_id
partition
duration_ms
```

字段按事件需要填写，不存在时保持为空。用户可读消息使用中文；程序筛选依赖稳定的英文 `event` 值，不能解析中文文本判断状态。

### 5. 存储与轮转

- 日志保存在项目根目录下独立的 `logs/` 运行目录，不与排行榜数据库、字幕、弹幕 XML 或总结结果混放。
- 默认同时输出控制台和按大小轮转的 UTF-8 日志文件。
- 日志文件设置单文件上限、保留数量和总量边界，防止长期运行占满磁盘。
- 多个短期采集进程写日志时避免相互截断；必要时按进程或日期拆分文件。
- 旧日志删除只由轮转策略负责，不由业务 Service 随意清理。
- 不新增常驻日志收集进程，不引入 Redis、ELK 或外部日志服务。

### 6. 脱敏与安全

日志不得记录：

- Cookie、API Key、Authorization 和完整请求头。
- WBI 原始密钥材料、签名参数和带敏感查询参数的完整 URL。
- `.secrets`、用户主目录等敏感绝对路径。
- 字幕全文、弹幕全文、模型完整提示词和完整响应正文。
- 未处理堆栈直接展示到 Web 页面。

客户端异常进入日志前统一转换为安全错误类型和摘要。详细堆栈只允许写入本地调试日志，并且仍须先脱敏。

### 7. 日常检查方式

后台日志不接入 Web 页面，不增加侧边栏入口，也不让网站读取日志文件。日常检查直接在项目目录中完成：

```powershell
Get-Content .\logs\app.log -Tail 100
Get-Content .\logs\app.log -Tail 100 -Wait
Select-String -Path .\logs\*.log -Pattern 'ERROR|WARNING'
```

日志文件名和目录保持稳定，并在 README 中说明常用检查命令。需要定位某个任务时，可以按 `task_id`、`run_id`、模块或事件名称搜索。日志不存在、正在轮转或包含损坏行时，只影响日志检查，不影响业务任务运行。

### 8. 实现边界

建议增加：

```text
app_logging/
├── __init__.py
├── config.py                  # handler、格式、级别和轮转配置
├── context.py                 # 任务 ID、run ID 等上下文字段
└── sanitization.py            # 敏感信息脱敏
```

业务模块只记录领域事件，不各自配置文件 Handler。日志初始化由 CLI 或 Web 入口统一执行，避免重复 Handler 导致同一条日志重复写入。

### 9. 异常与性能边界

- 日志写入失败不得让排行榜采集、总结或 UP 采集任务失败。
- 高频循环只记录汇总进度，不逐条记录 100 个榜单视频、全部字幕或全部弹幕。
- 网络重试记录次数、最终状态和安全错误类型，不重复输出相同完整异常。
- 多进程并发下允许不同日志文件最终合并展示，但时间和任务 ID 必须可追踪。

### 10. 测试

- 使用普通 pytest 函数测试日志结构、级别、上下文字段和轮转，不写测试类。
- 验证 Cookie、API Key、请求头、签名和敏感路径会被脱敏。
- 验证重复初始化不会添加重复 Handler。
- 验证日志写入失败时业务函数仍能安全运行。

## 十一、批次九：数据保留、隔离清理与数据库备份

> 排期规则：本批次始终放在最后。后续增加第九批或其他业务功能时，本批次编号继续顺延，不提前占用业务功能排期。

### 1. 目标

控制可重建缓存、运行日志和备份文件的长期磁盘增长，同时完整保留排行榜、长期趋势、UP 分析和视频总结所需的业务事实。第一版优先提供只读统计和清理预览，不自动删除数据。

### 2. 永久保留范围

以下内容不进入自动清理：

```text
data/ranking.db
data/summaries/
```

`ranking.db` 中的排行榜采集任务、分区结果、原始快照、榜单条目、UP 档案、历史投稿、指标快照、总结任务、执行尝试和最终结果全部长期保存。长期趋势和 UP 历史分析必须继续以原始事实为基础，不通过删除旧记录控制数据库大小。

### 3. 可隔离缓存

以下可重新下载或生成的中间文件默认保留 30 天：

```text
data/metadata/
data/subtitles/
data/transcripts/
data/danmaku/
data/danmaku_word_clouds/
```

缓存超过 30 天不代表立即删除。只有对应任务已经成功结束、数据库最终结果可解析、最终总结文件存在、没有活跃任务且文件未被占用时，才能进入隔离区。

### 4. 两阶段清理

符合条件的缓存先移动到：

```text
data/.retention_trash/
├── metadata/
├── subtitles/
├── transcripts/
├── danmaku/
└── danmaku_word_clouds/
```

隔离文件继续保留 14 天，确认没有影响后才允许永久删除。隔离目录加入 `.gitignore`。移动和删除均保留原始相对路径，便于人工恢复。

### 5. 清理安全条件

一个视频的中间文件必须同时满足以下条件才能隔离：

- 最后修改时间超过 30 天。
- 没有对应的 `PENDING` 或 `PROCESSING` 总结任务。
- 数据库中存在成功的总结任务，且 `result_json` 可以解析。
- 最终结果包含视频 ID 和结构化总结。
- 弹幕词云已写入最终结果，或明确标记为不可用。
- `data/summaries/{BV号}.json` 存在且可以解析。
- 文件没有被当前进程或任务锁定。

任一条件不满足时只报告原因并跳过，不尝试自动修复。

### 6. 执行模式

建议提供独立维护入口：

```powershell
python -m maintenance.retention --dry-run
python -m maintenance.retention --quarantine
python -m maintenance.retention --purge
```

参数边界：

| 参数 | 默认值 | 作用 |
|---|---:|---|
| `--cache-days` | `30` | 缓存进入隔离候选的最低年龄 |
| `--trash-days` | `14` | 隔离后允许永久删除的最低年龄 |
| `--dry-run` | 默认 | 只输出候选文件、大小和判断原因 |
| `--quarantine` | 关闭 | 将符合条件的缓存移动到隔离区 |
| `--purge` | 关闭 | 永久删除超过隔离期的文件 |
| `--video-id` | 空 | 只检查指定视频 |
| `--json` | 关闭 | 输出结构化报告 |

`--quarantine` 和 `--purge` 互斥。第一版上线后至少连续观察 7 天只读报告，再考虑启用隔离；永久删除默认保持人工触发。

### 7. 数据库监控与备份

数据库第一版只监控，不删除、不压缩历史事实。报告至少包括数据库大小、各表行数、每日新增榜单条目、每日新增 UP 快照、最早和最新时间，以及按当前增速估算的一年大小。

使用 SQLite Backup API 创建一致性备份，不直接复制正在写入的数据库：

```text
backups/ranking-YYYYMMDD-HHMMSS.db
```

建议保留：

- 每日备份保留 14 天。
- 每周备份保留 12 周。
- 每月备份长期保留。
- 每份备份完成后执行 SQLite 完整性检查。
- `backups/` 加入 `.gitignore`，不得提交数据库备份。

数据库达到 2 GB 等明确阈值后，再单独设计查询聚合或归档方案。在完成备份、恢复和长期趋势一致性验证前，不删除原始快照。

### 8. 日志保留

第六批产生的后台日志采用按大小轮转和 30 天保留策略。日志不进入数据库备份，不上传外部服务；过期日志可以直接由日志轮转机制删除，不进入视频缓存隔离区。

### 9. 测试

- 使用普通 pytest 函数测试年龄判断、任务状态判断、最终结果校验和路径边界。
- 使用临时目录验证只读预览不会移动或删除文件。
- 验证隔离保持相对路径，且 14 天内可以恢复。
- 验证永久删除只处理隔离目录内满足期限的文件。
- 使用临时 SQLite 验证备份和完整性检查，不操作真实数据库。
- 验证排行榜、UP、总结和所有 SQLite 业务表永远不进入清理候选。
- 验证符号链接、越界路径、活跃锁和损坏 JSON 均安全跳过。

### 10. 验收标准

- 默认运行只生成报告，不修改文件或数据库。
- 业务数据库、最终总结和长期分析所需原始事实不会被自动删除。
- 可重建缓存保留 30 天后只能先隔离，隔离 14 天后才能人工永久删除。

## 十二、九个模块的关联

```text

└── 弹幕词云

排行榜快照

└── 上榜 UP 识别
```

- 后台日志横向记录各模块的运行事件，但不替代各业务数据库中的任务状态和结果。
- 数据保留与备份依赖前述模块的存储边界稳定，因此始终在所有业务功能批次之后实施。
