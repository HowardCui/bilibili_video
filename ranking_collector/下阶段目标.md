# Ranking Collector 下阶段目标

## 一、总体目标

`ranking_collector` 的总体目标是：

> 每六小时采集 Bilibili 热门视频数据，保存历史快照，并通过前后快照对比，找出正在快速上升的视频和内容趋势。

它不直接面向网站用户请求 Bilibili。网站或小程序读取采集器已经保存的缓存结果。

## 二、数据流

```text
scheduler 定时触发
       ↓
service 组织采集
       ↓
client 请求 Bilibili
       ↓
models 转换为统一数据结构
       ↓
repository 写入 SQLite
       ↓
service 对比历史快照并计算趋势
       ↓
网站或小程序读取缓存结果
```

## 三、文件作用与实现目标

### 1. `config.py`

`config.py` 集中保存项目配置，目前已经包含：

- SQLite 数据库位置：`data/ranking.db`
- Bilibili 排行榜接口地址
- 时区：`Asia/Shanghai`
- 采集时间：每天 00、06、12、18 点
- 每个榜单获取 Top 10
- 目标分区：
  - 全站
  - 知识
  - 科技
  - 游戏
  - 生活

目标是让分区、采集时间和数据库位置等参数不散落在业务代码中。

### 2. `client.py`

`client.py` 负责和 Bilibili 通信，目前实现程度最高。

已经实现：

- 根据 `rid` 构造排行榜 URL
- 校验 `rid`、`limit` 和超时时间
- 请求 `ranking/v2`
- 校验 HTTP 和 JSON 响应
- 返回 `data.list`
- 将请求异常包装成 `RankingClientError`
- 全站接口出现 `-352` 时降级到 `/popular`

它的职责只包括：

> 请求外部接口，并返回原始或标准化数据。

它不应该写数据库、计算趋势或决定什么时候执行。

### 3. `models.py`

`models.py` 目前是空壳，目标是定义项目内部统一的数据结构。

至少需要定义：

- 视频基础信息
- 视频指标
- 榜单条目
- 采集快照
- 指标变化结果

一条视频数据应包含：

```text
BV 号
标题
UP 主
分区
发布时间
榜单排名
播放量
点赞数
投币数
收藏数
评论数
弹幕数
分享数
采集时间
```

这样其他模块就不必直接操作结构复杂的 Bilibili 原始 JSON。

### 4. `repository.py`

`repository.py` 目前是空壳，负责 SQLite 数据持久化。

需要实现：

- 创建数据库和数据表
- 保存一次采集任务
- 保存榜单快照
- 保存每个视频当时的指标
- 查询最近一次成功快照
- 查询某个视频的历史指标
- 查询两个时间点之间的变化

数据库可以先设计为三张核心表：

```text
collection_runs
记录每次采集是否成功以及错误信息

ranking_snapshots
记录某个时间、某个分区的一份榜单

ranking_items
记录快照中的视频、排名和各项指标
```

重要原则是快照不可覆盖。每六小时新增一份记录，才能计算历史趋势。

### 5. `service.py`

`service.py` 目前是空壳，是整个模块的业务核心。

它负责协调其他模块：

1. 读取启用的分区配置。
2. 调用 `client.py` 获取数据。
3. 使用 `models.py` 转换数据。
4. 调用 `repository.py` 保存快照。
5. 获取上一份快照。
6. 计算指标变化。
7. 输出本轮采集结果。

需要计算的趋势指标可以包括：

```text
播放增量 = 当前播放量 - 上次播放量

点赞增量 = 当前点赞数 - 上次点赞数

排名变化 = 上次排名 - 当前排名

每小时播放增量 = 播放增量 ÷ 两次采集间隔

互动增量 = 点赞 + 投币 + 收藏 + 评论等指标的增量
```

后续网站展示的“上升最快”和“热度增长最快”，主要来自这里。

### 6. `scheduler.py`

`scheduler.py` 目前是空壳，负责定时执行 `service.py`。

需要实现：

- 使用上海时区
- 每天 00、06、12、18 点执行
- 防止同一次任务重复运行
- 记录任务失败
- 程序重启后检查是否错过采集
- 必要时立即补采一次

它只负责“什么时候执行”，不应该直接请求 Bilibili 或操作数据库。

### 7. `ranking_collector_pipeline.py`

`ranking_collector_pipeline.py` 目前是空壳，是命令行启动入口。

理想情况下支持两种运行方式：

```powershell
# 立即采集一次，用于开发和调试
python -m ranking_collector.ranking_collector_pipeline --once

# 启动长期定时任务
python -m ranking_collector.ranking_collector_pipeline --schedule
```

它负责组装：

```text
client
repository
service
scheduler
```

但不应该包含具体采集逻辑。

### 8. `__init__.py`

`__init__.py` 用于把目录声明为 Python 包。

通常保持简单即可，不需要放业务实现。

## 四、当前完成度

目前的实现情况：

- `config.py`：基本完成
- `client.py`：已具备初步采集能力
- 其他核心文件：仍是空壳

因此当前模块可以尝试获取一份榜单，但还不能：

- 保存历史快照
- 计算趋势
- 每六小时自动执行
- 为网站或小程序提供稳定缓存数据

## 五、下一阶段目标

下一步优先实现 `models.py` 和 `repository.py`，先达到以下里程碑：

> 手动运行一次采集后，可以在 `data/ranking.db` 中看到一份完整榜单快照。

建议实施顺序：

1. 在 `models.py` 中定义统一数据模型。
2. 在 `repository.py` 中创建 SQLite 表结构。
3. 实现快照和榜单条目的原子写入。
4. 实现最近一次成功快照查询。
5. 在 `service.py` 中串联采集、转换和保存流程。
6. 完成一次手动采集验证。
7. 再实现指标变化计算和定时调度。
