# 本地综合网站完整设计（Shiny Core）

## 1. 目标与范围

建设一个仅限本机访问的综合网站。用户启动 Python 服务后，通过
`http://localhost:8000` 使用排行榜和视频总结功能。

第一阶段同时交付：

- 排行榜页面，读取现有 SQLite 榜单数据并展示实时比较结果。
- 视频总结页面，对接现有 Bilibili 视频处理与 AI 总结流水线。
- 持久化的视频总结任务、进度、结果、自动恢复和手动重试。
- 参考 Portfolio Dashboard 图片的深色、橙金色仪表盘视觉。

网站不包含公网部署、用户系统、网页内采集控制、密钥编辑、ASR、向量问答和多用户任务调度。

## 2. 技术选择

网站使用 Shiny for Python 的 Core 模式实现，不使用 React、Vite、Tailwind CSS、TypeScript 或 FastAPI。

选择 Shiny Core 的原因：

- 项目现有功能全部使用 Python，Shiny 可以直接复用现有模块。
- 排行榜、SQLite、后台任务和响应式状态更新可以留在同一技术栈内。
- UI、Server、Service 和 Repository 仍可按功能拆分，不需要写成单文件应用。
- 可通过自定义 HTML 和 CSS 实现参考图的仪表盘风格。
- 后续可以继续增加 UP 主分析、长期趋势、通知、搜索和问答模块。

Shiny 是网站展示和交互层，不替换现有业务逻辑。

## 3. 现有模块复用

```text
Shiny 页面
  ↓ 调用
web_app 服务和查询层
  ↓ 复用
ranking_collector/   排行榜采集、存储、调度和快照比较
video_processing/    元数据、字幕和文字稿处理
summarization/       分段总结与合并总结
```

保留以下行为：

- 排行榜采集、SQLite 快照和实时比较逻辑。
- 每日调度和启动补采判断。
- 匿名请求优先、失败后读取 `.secrets/bilibili_cookies.txt`。
- 单视频元数据、中文字幕、文字稿、分段总结和合并总结流程。
- 原有 `--once` 和 `--schedule` CLI 运行方式。

新增的代码只负责网页、网站查询和持久化总结任务。

├── ranking/
│   ├── __init__.py
│   ├── ui.py                    # 排行榜页面 UI 构建函数

│   └── queries.py               # 排行榜只读查询与页面数据组装
├── summary/
│   ├── __init__.py
│   ├── ui.py                    # 视频总结页面 UI 构建函数
│   ├── server.py                # 提交、刷新、重试和结果渲染
│   ├── repository.py            # SQLite 总结任务持久化
│   └── service.py               # 去重、后台执行、恢复与重试

`web_ui/` 只保存网页设计、实施计划和手动验收文档；实际 Shiny Python 与 CSS 代码放在 `web_app/`。

文件按功能边界拆分。`app.py` 只负责组装 App、注册两个页面和管理应用生命周期，不包含排行榜 SQL 或总结流水线细节。

## 5. 编码约束

- 类不使用装饰器，包括不使用 `@dataclass`。
- Shiny 官方函数装饰器可以正常使用，包括 `@render.*`、`@reactive.effect` 和 `@reactive.event`。
- 测试全部使用普通 pytest 函数，不写测试类。
- UI 尽量由普通 Python 构建函数组成。
- 后台任务、查询和数据转换优先写成可独立测试的普通函数。
- Shiny 响应式函数只负责读取输入、调用普通函数和渲染结果，不承载复杂业务规则。

## 6. 应用框架与导航

桌面端采用参考图中的窄侧栏布局：

- 顶部显示网站标志。
- 主导航包含“排行榜”和“视频总结”。
- 当前入口以橙色竖线、图标高亮和可访问状态共同标识。
- 底部保留服务状态或帮助入口。

平板端收窄侧栏，只显示图标和提示文字。手机端改为底部双入口导航，内容区域占满可用宽度。

导航使用 Shiny Core 的导航组件或隐藏导航容器实现，页面切换不重新启动后台任务。

## 7. 视觉系统

参考图只定义视觉语言，实际内容替换为排行榜和视频总结。

### 7.1 风格

- 页面背景使用暖橙色外框，应用主体使用炭黑色大圆角容器。
- 侧边栏、内容区和信息卡通过不同层级的深灰色区分。
- 橙色为主要操作与主趋势强调色，金黄色为次级指标色。
- 绿色表示成功或正向增长，红橙色表示失败或负向变化。
- 文字分为高亮标题、正文、辅助说明和弱化元数据四个层级。

### 7.2 设计 Token

CSS 变量统一定义：

- 页面、侧栏、内容面板和悬浮卡片背景。
- 主色、次强调色、成功色、失败色和警告色。
- 4 像素基础间距体系。
- 小、中、大三档圆角。
- 面板边框、柔和阴影和键盘焦点环。
- 快速反馈、阶段切换和页面过渡三档动画时长。

Shiny 生成的 Bootstrap 元素通过局部 CSS 类覆盖，不使用影响整个页面的无边界选择器。

## 8. 排行榜页面

### 8.1 页面结构

- 顶部展示页面标题、当前快照时间、数据新鲜度和分区切换。
- 主区域展示排名趋势、播放增长或快照变化。
- 右侧摘要显示换血率、快速上升、新进榜和其他核心指标。
- 下方状态卡展示持续在榜、新进榜、跌出榜、排名变化和每小时播放增长。
- Top 100 使用可横向滚动的数据表，至少展示排名、标题、UP 主、播放、点赞、投币、收藏、评论、弹幕和分享。

分区至少包含全站、知识、科技、游戏和生活。

### 8.2 数据链路

```text
选择分区
→ 查询最新成功快照
→ 查询上一份成功快照
→ 调用现有比较逻辑
→ 组装独立页面数据
→ Shiny 渲染输出
```

页面不直接执行 SQL。`queries.py` 调用 `ranking_collector.repository` 和 `ranking_collector.service`，把内部模型转换为页面数据。

### 8.3 状态展示

- `CURRENT`：当前有效比较。
- `LAST_VALID`：展示上一份有效比较，并明确来源时间。
- `NO_BASELINE`：没有可供比较的上一份快照。
- `STALE`：快照间隔超过 24 小时，继续展示变化但不显示有效换血率。
- `EMPTY_CURRENT`：当前榜单为空，不把上一份全部判断为跌出榜。

数据库为空时显示可读空状态和 CLI 采集提示。不存在的分区或快照显示明确错误状态，不让整个 Shiny 会话崩溃。

## 9. 视频总结页面

### 9.1 提交与任务展示

- 顶部提供 Bilibili URL 输入框和“开始总结”按钮。
- URL 为空或不是受支持的 Bilibili 链接时，在输入区就近提示。
- 点击后创建或复用 SQLite 任务，响应式处理不直接执行长流程。
- 当前任务卡显示视频信息、任务状态、当前阶段、更新时间和可用操作。
- 历史任务列表显示视频标题、状态、提交时间、完成时间和结果复用标记。
- 页面定时读取 SQLite；任务进入终态后降低或停止当前任务的高频刷新。

### 9.2 处理阶段

```text
等待执行
→ 获取视频元数据
→ 获取中文字幕
→ 解析文字稿
→ 切分文字稿
→ 分段总结
→ 合并总结
→ 完成
```

### 9.3 状态动画

- 等待或重新排队：柔和呼吸效果。
- 处理中：橙金色环形加载动画、当前阶段文字和进度轨道。
- 成功：短暂绿色完成动画，随后展开总结结果。
- 失败：红橙色错误动画，轻微抖动一次后显示稳定失败标记。
- 所有动画遵守 `prefers-reduced-motion`，减少动态效果时改用静态图标和即时状态变化。

失败动画不得持续闪烁，不得妨碍用户阅读错误或点击重试。

### 9.4 结果展示

成功结果按结构化区块展示：

- 视频基本信息。
- 一句话总结。
- 详细内容总结。
- 分章节总结。
- 关键观点。
- 关键词。
- 重要时间点（结果存在时）。

页面不显示元数据、字幕、文字稿或总结文件的本地绝对路径。

## 10. 总结任务持久化

SQLite 保存总结任务和执行记录：

- 任务 ID、规范化 BV 号和原始 URL。
- 状态、当前阶段和公开错误信息。
- 结构化总结结果。
- 创建、开始、更新和完成时间。
- 重试关系及结果复用来源。

状态流转为：

```text
PENDING → PROCESSING → SUCCEEDED
                     ↘ FAILED
```

### 10.1 去重与复用

- 同一 BV 号最多存在一个活跃任务。
- 重复提交正在处理的视频时返回已有任务。
- 已有成功结果时默认直接复用，避免重复调用模型。
- 手动重试失败任务时保留旧执行记录，并创建关联的新执行尝试。

### 10.2 后台执行

- Shiny 响应式函数不执行同步长任务。
- 应用级后台执行器领取 SQLite 任务并调用现有总结流水线。
- 总结流水线通过进度回调更新任务阶段。
- 数据库状态是页面和执行器之间的事实来源。
- 写入使用短事务，减少与排行榜读取之间的锁竞争。

### 10.3 重启恢复

- 服务启动时扫描 `PENDING` 和遗留的 `PROCESSING` 任务。
- 遗留 `PROCESSING` 先安全转换为 `PENDING`，再自动排队。
- 恢复过程保持幂等，重复启动不会产生多个活跃执行。
- 用户仍可对失败任务手动重试。
- 服务关闭时停止接收新任务；未完成任务保留供下次启动恢复。

## 11. 安全与异常

- 服务启动命令固定监听 `127.0.0.1:8000`，不得默认监听 `0.0.0.0`。
- Cookie、API Key、堆栈、原始模型错误和敏感本地路径不得进入页面。
- Cookie 继续匿名请求优先，失败后才读取 `.secrets`。
- 排行榜页面只读，不提供采集器或调度器控制。
- 无中文字幕显示稳定的用户错误，不暴露内部异常。
- SQLite、网络和模型错误经过安全转换后再显示。
- 单个输出渲染失败时显示局部错误状态，不主动终止整个会话。

## 12. 自动测试设计

不使用 Playwright 或其他浏览器自动化。所有自动测试均为普通 pytest 函数，不写测试类。

### 12.1 Repository 测试

- SQLite 表初始化和重复初始化。
- 任务创建、查询、列表和条件状态更新。
- 同一 BV 号只能有一个活跃任务。
- 结果 JSON 保存与读取。
- `PROCESSING` 重启恢复为 `PENDING`。
- 重试关系和旧执行记录保留。

### 12.2 Service 测试

- Bilibili URL 校验和 BV 号规范化。
- 新任务创建、活跃任务复用和成功结果复用。
- 后台执行成功、失败和阶段更新。
- 启动自动恢复、关闭停止接收新任务。
- 失败任务手动重试。
- 公开错误不含敏感内容。

真实网络、Cookie 和模型调用通过依赖注入替换为确定性函数，不在测试中调用外部服务。

### 12.3 排行榜查询测试

- 空数据库与暂无数据状态。
- 五个启用分区的最新 Top 100。
- 正常、无基线、陈旧、空当前榜单和上一份有效比较。
- 排名变化、每小时播放增长和换血率状态。
- 无效分区与不存在快照。

### 12.4 Shiny 边界测试

复杂交互判断提取成普通函数并测试：

- 分区输入到页面数据的转换。
- 任务状态到显示文案、CSS 状态和可用操作的转换。
- 总结结果到展示区块的转换。
- 提交、重试和刷新函数对 Service 的调用结果。

自动测试不依赖浏览器 DOM，也不测试 Shiny 框架自身行为。

- 五个分区切换、Top 100 和各比较状态。
- 视频提交、去重、历史任务、手动重试和结果展示。

## 14. 扩展边界

后续功能继续按模块添加，例如：

```text
web_app/
├── uploader/          UP 主历史分析
├── trends/            长期趋势
├── notifications/     通知与报告
└── search/            搜索与问答
```

每个模块分别包含 UI 构建函数、Server 绑定、Service、Repository 和普通函数测试。模块通过稳定的 Python 接口复用现有业务能力。

如果未来转向公网、多用户和高并发，再考虑拆分 API、独立任务进程和外部队列；当前本地单用户阶段不提前引入这些复杂度。

## 15. 验收标准

- `http://localhost:8000` 可打开网站，服务只监听本机地址。
- 侧边栏具有排行榜和视频总结两个入口，手机端有适用的导航形式。
- 排行榜读取现有 SQLite，可切换五个分区并查看 Top 100 和比较状态。
- 空数据、陈旧数据、失败分区和空榜单均有清晰状态。
- 可以提交 Bilibili URL，并看到持久化任务的状态、阶段和动画。
- 服务重启后未完成任务自动重新排队，失败任务可手动重试。
- 重复视频任务得到去重，已有成功结果得到复用。
- 成功结果结构化展示，失败信息不泄露敏感数据。
- 自动测试全部使用普通 pytest 函数并通过。
- 原有采集、调度、视频处理和总结逻辑继续复用且测试不回归。
- 用户按照手动验收清单确认桌面、平板和手机页面。
